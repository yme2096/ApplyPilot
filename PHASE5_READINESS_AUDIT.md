## Controls observed

- **Authentication/authorization:** Spring Security is stateless; all non-auth, health, error, and preflight requests require authentication. CORS is restricted to the configured single origin. Passwords use BCrypt cost 12. JWT secret fails closed below 32 bytes. Refresh tokens are random, stored as hashes, rotated, and revoked on logout/reset.
- **Password reset:** Reset tokens are random, hashed, single-use, expire after 30 minutes, and a successful reset revokes refresh tokens. The public request behavior avoids account enumeration when configured; missing SMTP returns a controlled 503.
- **Data isolation:** Controllers generally scope queries by authenticated user; V10/V11 add composite owner foreign keys. Existing API ownership integration checks passed. Profile dynamic SQL uses a fixed server-side table/field allowlist and parameterized values.
- **File authorization:** Resume routes require auth and verify resume ownership. This review found stored download keys were normalized but not checked to remain within the upload root; the current source now checks normalized and resolved paths. Tests cover traversal rejection and a valid in-root read.
- **Logging:** The resume parse error path previously logged worker response bodies and exception messages, which could contain extracted resume text. Current source logs only status or a static failure message. Other reviewed ingestion logs avoid dumping response bodies; keep this rule in future code.
- **SQL/XSS:** Reviewed value-bearing SQL uses placeholders; the dynamic profile query identifiers come from fixed maps. No production `dangerouslySetInnerHTML` use was found; React text rendering escapes content. Automated scanning and penetration testing were not performed.
- **Extension:** Manifest V3 permissions are limited to local app and named ATS hosts; the extension stores tokens in `chrome.storage.session`, not local storage, and requests profile data on demand. `tabs`/`scripting` are used by the popup's active-tab detection fallback. Live Chrome/ATS behavior remains NOT TESTED.
- **Containers/secrets:** API and worker images run as non-root. `.env` is ignored by Git and Compose requires `JWT_SECRET`, but local DB defaults and host port bindings are not suitable for production. The running local stack has not been restarted for this audit.

## Proposed Phase 5 milestones

1. **Security remediation:** Patch vulnerable developer tooling; add API rate limits; decide access-token revocation and reset-link token handling; add CSP/headers; lock down local Compose bindings and design a separate production deployment. Add tests for each security control.
2. **End-to-end tests:** Add browser tests for registration/login/session expiry, imports, resume version selection, bulk review, application tracking, follow-ups, reminders, and extension-to-local-API flows. Keep employer submission out of automation.
3. **Performance and reliability:** Measure representative database query plans; test bounded worker/API timeouts, concurrency, upload limits, notification scheduling, and API readiness. Add indexes only after measurement.
4. **Error recovery:** Exercise API/worker/cache interruptions, stale auth, retry/idempotency, migration interruption, and safe user-visible recovery. Keep AI optional and provider failures controlled.
5. **Deployment preparation:** Build a separate production configuration with TLS ingress, private service networking, required secrets, least privilege, image/dependency scanning, monitoring, backups, and a successful isolated restore drill.
6. **Documentation and operations:** Publish a deployment runbook, backup/restore and incident procedures, migration checklist, security disclosure/contact, dependency update process, and explicit non-production limitations.

**Readiness decision:** Not production-ready. Phase 5 is in progress. Some P1 items have been addressed, but remaining risks and missing deployment/restore evidence must be resolved before considering any public deployment.
